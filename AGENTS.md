# Working on pruzhany-schema

Read this file before changing anything. These shared rules apply to Claude Code and
Codex; where a skill's or a tool's defaults differ, this file holds.

## The three repositories

- **pruzhany-steps** holds the record, the pipeline and the one plan, `PLAN.md`.
  Its `decisions/` holds the cross-repository decision record; `.scratch/<plan>/`
  holds working notes and results.
- **pruzhany-schema** holds the LinkML data model and contracts consumed by both
  other repositories. Read [README.md](README.md) and [linkml/README.md](linkml/README.md).
- **pruzhany-svelte** is the website; its data is generated by pruzhany-steps.

The model must grow to cover every kind of data and exchange: physical pages,
regions, lines, words and boxes; semantic items and what they name; provenance
(sources, readings, corrections); model exchanges; and products (pruzhany-steps
decision 214, decision 28 of its map).

## Stay close to EHRI and RiC-O

- Prefer an EHRI class where EHRI has one; otherwise use a RiC-O term present in
  EHRI's RiC-O version; otherwise declare a local term in a profile and give a reason.
- Read the ontology through `standards/` before mapping; never map from memory.
- Read and add a new EHRI or RiC-O version as a new `standards/` file only at the
  owner's word, then re-check every mapping. Never edit a pinned list in place.
- An owner-approved vocabulary addition names its mapping. Run `bin/verify standards`
  for every mapping change.
- Persons, life events and relations are being vetted: use the standards' shapes, with one identity
  per person across issues and tests of meaning. Before changing how any of them is
  identified, shaped or related, read the [standards foundation vetting](docs/design/2026-10-23-standards-foundation-vetting.md)
  and [ADR 0001](docs/adr/0001-which-standard-governs-what.md).

## Privacy and vocabulary approval

- **Nothing about real people goes into this public repository or its issues during
  the build-out.** Working notes, examples and evidence about real people go to
  pruzhany-steps. An issue, design note or test here names the type, the field and its
  mapping, with fictional examples. What is already here stays as it is
  (pruzhany-steps decision 214, decisions 10 and 23 of its map).
- New vocabulary types need the owner's approval in batches, each with its mapping;
  use the [approval record](docs/vocabulary-approvals.md). Keep each type's two or
  three real examples in pruzhany-steps and show them to the owner privately, never
  put them here. Until approval, a fact stays `other` with its `proposed_type`.
  A released type is never removed or renamed.

## Contracts and preservation

- The LinkML definition in `linkml/schema/` is the one definition of the record's
  data. Change it first; vocabulary enums start in `vocabulary/*.json`, whose
  generator writes `linkml/schema/vocabulary.yaml`.
- Regenerate with `linkml/generate.py` using the [locked environment and commands](linkml/README.md#commands).
  Never edit generated files. Keep Zod and Python twins in step with the definition
  and each other; their retained refinements and rules remain the runtime validators.
- Preserve the wire behavior of pages and blocks, cross-references and external
  references. Keep released vocabulary and snapshots, standards pins, LLM extraction
  models and the isolated sourced-entities pilot intact. The pilot stays isolated
  from production models. [README.md](README.md#current-site-files) describes the
  four issue documents, shared record, module locations and retired contracts.
- Before adding or changing tests under `zod/`, read the [bun-only test rules](.claude/rules/zod-tests.md).
  Both agents must follow them.

## Set up and verify

With mise and uv installed, run from the repository root:

```sh
mise install
bun install --frozen-lockfile
bin/verify
```

Use the versions in `mise.toml`; bash, git and uv are also required. See
[verification](docs/agents/verification.md) for setup details and consumer commands.
`bin/verify` is the single verification entry point, including standards alignment;
its header describes all nine steps and their toolchain. `bin/verify <step>...`
runs selected steps while working; run the full check before merging. The `entities`
step checks sourced assertions in the current `SiteArchive` carrier, and `contract`
runs Zod↔Pydantic lockstep here.

**A change here is checked against its consumers before it merges.** Run the five
pruzhany-svelte checks in [verification](docs/agents/verification.md#consumer-checks)
against this checkout's schema files. In pruzhany-steps, `site_shapes refresh`
requires a clean committed schema HEAD; preview generated differences separately
until that commit exists. Consumer checks run separately from `bin/verify`.
